How agents finish a job

A short talk for developers delegating a complete change

This talk follows one hypothetical booking change. The question is what must happen after code has been written before someone can assess the finished job. No customer incident or productivity measurement is presented.

The request is small.
The promise isn't.

“Let a customer move a booking.”

Changing the time must not lose the booking.

Our invented customer already has a booking. Moving it is a state change, not just a calendar selection. The destination can become unavailable, and a failed move must preserve the original appointment.

First, define what
must survive.

Keep the old slot

Release it only when the move succeeds.

Use the booking service

Keep access and state changes together.

Notify after success

A refused move must not send a confirmation.

These are the assumptions of this example. Real projects need their actual booking and payment contracts. Set the rules before asking the agent to design the flow, so implementation doesn't silently choose the product behavior.

The screen doesn't
own the booking.

Put the transition in the service that owns it.

The diagram makes the boundary explicit. The form submits the requested move. The booking service enforces access and coordinates the calendar transition; it must not release the old slot on a failed reservation. The exact atomic mechanism belongs to the real system, not this diagram.

Check the service.
Then use the screen.

Service checks

  • The complete interval is available.
  • A taken destination is refused.
  • Another customer can't move it.

These are proposed checks for the invented feature, not test results. Service tests and a rendered customer flow answer different questions. Follow the real control through confirmation and inspect the stored booking rather than infer success from a button click.

14:00 is gone.

The customer still has 10:00.

Refuse the move. Keep the booking. Offer another time.

Another customer may reserve the destination after it was displayed. Refusal is the correct result in that case. This failure path is part of finishing the feature, not an optional edge to revisit after the happy path looks polished.

This is the shape of an example handoff, not a report that those application checks ran. A real handoff should identify the actual change, connect observed evidence to its version, and state the remaining decision. The reader can then assess readiness without rebuilding the conversation.

Finish
the promise.

Leave working behavior
and the evidence to judge it.

The agent's task is finished when it has reached the agreed outcome and left enough evidence to judge the result. That can include a visible remaining release decision if release was not part of the authorization. Keep the task's actual scope intact.
